2. El recómputo triple sí merece una unidad pequeña

La intervención que propones es razonable: calcular una vez el mismo write que ahora se calcula tres veces, sin cambiar las tres operaciones que lo consumen.

La llamaría:

STATE-PRELUDE-WRITE-REUSE

Su baseline será hoist + SIMD ya congelado.

Alcance exacto

Para cada combinación de worker, elemento del batch y posición temporal del backward:

1. Obtener el estado guardado correspondiente a esa posición.
2. Usar su mean_state con la misma ruta actual.
3. Calcular write[0:1024] una sola vez
   mediante state_prelude_write existente.
4. Reutilizar ese vector en:
       pre_norm_sum
       norm_dot
       d_pre
5. Reutilizar el espacio para la siguiente combinación.

No calcularlo una vez para toda la ventana. El estado y token_part cambian con la posición temporal. Tampoco se debe reconstruir desde un buffer de estado que ya haya sido sobrescrito con gradientes: debe usar las mismas entradas guardadas que utiliza actualmente cada recomputación.

En este primer cambio guardaría write tal cual, sin aprovechar para fusionarlo con el residual, reformular RMSNorm o alterar el orden de sus sumas. Mantener el cálculo existente y sus puntos de redondeo reduce la superficie de cambio numérico; /fp:precise también restringe transformaciones que alterarían resultados de punto flotante.

Buffer pequeño y privado

Un vector de 1,024 valores FP32 ocupa:

1024×4=4096 bytes=4 KiB.

Si cada worker procesa un elemento del batch por vez, basta un scratch de 4 KiB por worker, reutilizable entre posiciones. Con cuatro workers serían 16 KiB adicionales.

Debe estar declarado en el cálculo de workspace y reservado antes del camino medido. Nada de allocations por timestep ni buffer global compartido. Tampoco reutilizaría otro buffer sin demostrar que ya terminaron todas sus lecturas: ese tipo de aliasing ya provocó errores en esta campaña.
