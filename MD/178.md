Mi decisión sobre las tres es distinta.

Teacher forward único

Sí, Addendum 197 autorizó investigar teacher reuse; no lo convirtió en la ruta científica.

La idea es correcta algebraicamente: un forward del teacher con 0:512 contiene logits de ambas ventanas.

Pero hay un coste oculto: para B=8, el tensor completo de logits 512×50257 FP32 es enorme. Y para aprovecharlo en window1 después del optimizer step habría que conservar aproximadamente media salida o materializar targets equivalentes.

Esto puede ahorrar cómputo y al mismo tiempo empeorar la presión de memoria que ya causó varios hard stops.

Por eso sigue siendo una excelente optimización para medir, pero no la metería antes de ER64 Quality-A, porque además introduciríamos una implementación de teacher distinta de aquella que produjo los baselines R1.

Primero terminemos la comparación arquitectónica limpia.

Compartir teacher K1/K4

No lo haría.

El ahorro teórico es claro, pero obliga a:

cache persistente;

IPC;

productor común;

o ejecutar K1/K4 acoplados.

Todo eso complica la independencia que tantos bugs nos ayudó a preservar.

No vale la pena ahora.

Threads 1/2/4

Sí merece benchmark, especialmente después de este bug.

Pero la regla sería:

escoger un único número de threads para toda la plataforma futura, usando únicamente coste técnico.

Nunca:

K1 = 1 thread
K4 = 4 threads
ER64 = 2 threads

porque introduciríamos backend por variante.

Para Quality-A actual mantendría 4/1, para máxima comparabilidad con R1/ER32 históricos. El sweep puede servir para una futura campaña realizada completamente de cero.
