**Recomendación concreta: GHCR privado**

Usaría GitHub Container Registry, bajo la cuenta del usuario y con visibilidad privada, aprovechando que el proyecto ya está en GitHub. Es una recomendación de publicación, no una autorización implícita para subir contenido ni crear credenciales.

GHCR permite controlar la visibilidad del paquete y separar permisos de publicación y lectura. Para este flujo, el VPS necesita permiso de publicación; RunPod sólo necesita lectura. No debe recibir una credencial con capacidad de escribir o borrar imágenes.

2. Registrar el digest que devuelve el registro.
3. Verificar que puede descargarse por ese digest con las credenciales de lectura previstas.
4. Comprobar que corresponde a la imagen validada, sin reconstruirla ni actualizar dependencias.

**No exigir información que el proveedor sólo determina al asignar el host**

Aquí conviene evitar otro bloqueo artificial.

No necesitamos conocer de antemano el modelo exacto de CPU o el identificador de la máquina física. Si el proveedor asigna el host al crear el Pod, puede bastar con conocer y poder fijar los mínimos de recursos aceptados para la oferta.

La API oficial de RunPod contempla, entre otros, minVCPUPerGPU, minRAMPerGPU, containerDiskInGb, dataCenterIds y networkVolumeId. Esos campos permiten expresar restricciones del despliegue; su existencia no equivale a que ya haya una máquina asignada.

El informe debe distinguir:

- Recursos ya descritos por la oferta.
- Mínimos solicitables y aceptados por el proveedor.
- Características que se comprobarán después de la asignación.

Una consulta de consola previa a confirmar el despliegue o una respuesta de disponibilidad compatible puede completar lo que no exponga la herramienta actual. No se autoriza crear un Pod "para descubrir" su precio o sus recursos.

Si no se puede establecer una oferta compatible con un coste y unos recursos suficientemente definidos, mantener quote_usable=false y explicar exactamente qué falta. No inventar CPU/RAM ni presentar los valores predeterminados de una API como una garantía de la oferta.

## 4. La ausencia de self-hash no justifica repetir la validación

Coincido en no bloquear el cierre por ese campo ausente, pero haría una precisión: la verificación en vivo y el hash del artefacto cubren aspectos distintos. Una comprueba el entorno; el otro identifica los bytes del registro.

No hace falta modificar retrospectivamente validation_manifest.json. En el próximo registro de lanzamiento, incluir su SHA-256 externo calculado desde el archivo original, junto con el commit de procedencia y la identidad de la imagen.

Eso mantiene la trazabilidad sin reabrir el build ni entrar en otro ciclo de auto-hashes. La imagen tampoco necesita reconstruirse para añadir metadata a un informe externo.
