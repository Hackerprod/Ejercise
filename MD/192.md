Sí. Confirmo DIRECTIONAL-STOP como cierre formal. No hay base metodológica para suavizarlo: el criterio predeclarado decía que δ16 > +0.10 era STOP sin importar el ahorro técnico, y terminó en +0.379. El ~11% de ahorro y −62.8% RSS son reales, pero no compensan una degradación lingüística de ese tamaño.

La lectura más importante es que TBPTT16 no parece simplemente “más lento para aprender”. La curva apunta a otra cosa:

FULL-BPTT:
10.92 → 7.48 → 6.96 → 6.80 → 6.74

TBPTT16:
10.92 → 7.51 → 7.10 → 7.05 → 7.12

Entre 1000 y 2000, full-BPTT sigue aprendiendo mientras TBPTT16 prácticamente entra en un plateau y luego retrocede. Eso es compatible con que el horizonte de 16 esté sesgando el gradiente demasiado hacia dependencias locales. El estado sigue viajando hacia adelante entre chunks, pero después de cada detach() el modelo ya no recibe crédito hacia atrás por efectos que cruzan esa frontera. Puede “recordar” algo en forward, pero no aprender correctamente qué transformaciones anteriores fueron responsables de que ese estado resultara útil 32, 64 o 128 tokens después.

No lo atribuiría exclusivamente a “dependencias largas” todavía. También son plausibles la interacción con K4, el sesgo acumulado de 16 backprops parciales por update y una geometría de optimización distinta. Pero los datos no parecen un caso de “dale otros 1000 updates y alcanza”; eso es precisamente lo que la forma de la curva desaconseja.

Sobre el runtime C++: ya no exigiría implementar bptt_horizon configurable en Prioridad 2. Esa condición la habíamos puesto explícitamente sólo si el probe no salía negativo. Salió negativo.

Para v1 del runtime nativo haría:

training semantics = full BPTT actual
window = 256
detach únicamente en las fronteras ya canónicas
sin soporte TBPTT 8/16/32

Esto evita construir complejidad para una técnica que acaba de fallar su screening.

Pero dejaría una seam arquitectónica, no una feature implementada. Por ejemplo, que el loop temporal no esté escrito de una manera que haga imposible introducir después una frontera de detach configurable. No hace falta:

código TBPTT;

tests para 8/16/32;

buffers especiales;

kernels alternativos;

lógica runtime de horizon.

Sólo evitar un diseño deliberadamente acoplado a “jamás habrá cortes internos”.

Porque una cosa importante sigue siendo cierta: este experimento sólo responde sobre:

K=4,seed=20260913,horizon=16.

No demuestra que horizon=32 falle, ni que K1 responda igual. Pero según el árbol que fijamos, no tenemos suficiente razón para pagar ahora ese sweep. Si en el futuro otro resultado hace especialmente valioso revisar TBPTT32, se abre una unidad nueva.
