Hay un detalle de tu implementación que me hace sospechar

Mencionaste un gather vectorizado para un backward leyendo una matriz transpuesta.

Para GEMM denso, intentaría no usar gather en absoluto.

Con pesos row-major W[out,in], las cuatro rutas deberían estructurarse aprovechando cargas contiguas:

Forward
Para varios outputs simultáneamente:

load x[i:i+8] una vez
load W[o0,i:i+8]
load W[o1,i:i+8]
load W[o2,i:i+8]
load W[o3,i:i+8]
→ 4 acumuladores

Es decir, tile de 4 outputs × 8 inputs. Eso reutiliza x y aumenta ILP.

dInput

En vez de calcular cada dX[i] haciendo gather de una columna de W:

for output o:
    broadcast dY[o]
    load W[o, i:i+8] contiguo
    dX[i:i+8] += dY[o] * Wrow

Aquí todo son cargas contiguas. Para una matriz densa, un gather suele ser señal de que el orden de loops puede mejorarse.

dWeight

Outer-product:

xvec = load x[i:i+8]

for outputs o0..o3:
    dy = broadcast dY[o]
    dW[o,i:i+8] += dy * xvec

De nuevo, ninguna gather.

dBias

Vectorizar sobre outputs:

dbias[o:o+8] += dY[o:o+8]

en lugar de hacer una reducción horizontal por bias.

Eso rompe la dependencia sin convertir cada dot-product en muchas operaciones de horizontal-sum.

Mi sospecha concreta

El enfoque actual de “acc0..acc3 para romper la dependencia” es correcto como primer AVX2 funcional, pero puede seguir siendo un microkernel pobre si:

hace gathers;

calcula un output por vez;

hace horizontal reduction muy frecuentemente;

no reutiliza x entre varias filas de pesos;

relee pesos/input más veces de las necesarias.

Por eso no replicaría automáticamente esa plantilla en FC2.

Si dInput con gather sale mucho peor que los demás, la corrección probablemente sea el loop-order contiguous que describí arriba.

No usaría todavía blocking más complejo de caché

Primero haría register tiling + contiguous loads + loop-order correcto. D=128 y H=512 son tamaños muy amistosos para AVX2:

128 = 16 × 8;

512 = 64 × 8;

no hay prácticamente necesidad de tails en estas matrices principales.
