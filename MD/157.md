## 2. La desviación más importante no es la imagen: es la secuencia de ventanas

En run_preflight() aparece:

```python
for update in range(updates):
    window = 0 if update == 0 else 1
```

Eso produce:

```
Ejecutado:  0, 1, 1, 1, 1, 1, 1
Acordado:   0, 1, 0, 1, 0, 1, 0
```

El mismo código conserva state entre actualizaciones y sólo lo reinicia dentro de microbatch_update() cuando window == 0. Por tanto, después de la primera pareja, se vuelve a recorrer la segunda ventana utilizando el estado que quedó después de haberla recorrido anteriormente.

**Por qué esto afecta la causalidad**

En la segunda ventana se intenta predecir, por ejemplo, x_257 después de procesar x_256.

La primera vez, el estado previo corresponde al prefijo anterior y eso es correcto. La siguiente vez, el estado conservado ya recibió x_257 y otros tokens posteriores durante la pasada anterior.

Es decir: estado que ya vio parte del objetivo futuro → volver a predecir ese objetivo.

El detach() corta el gradiente, pero no borra esa información del estado.

Además, el maestro vuelve a evaluar el prefijo original, mientras que el estudiante tiene un historial recurrente diferente. Ya no están aprendiendo la misma distribución condicionada al mismo prefijo.

Esto no demuestra que el estudiante haya explotado esa información en siete pasos. Sí demuestra que el runner permite información futura respecto de la posición que pretende predecir. Es un defecto del entrenamiento, no una limitación de R1.

Estas omisiones también escaparon a mis revisiones anteriores del lanzador. No debí darlo por conforme únicamente porque reutilizaba el core y la pérdida ya revisados.

## 3. Hay otras dos diferencias que deben registrarse

**AdamW no está configurado con weight_decay=0**

El lanzador construye:

```python
optimizer = torch.optim.AdamW(student.parameters(), lr=BASE_LR)
```

No especifica weight_decay. La documentación de PyTorch 2.11 establece su valor predeterminado en 0.01, no en cero. Por tanto, con el código versionado, la afirmación de que se conservó weight_decay=0 no queda sustentada.

La corrección es hacer explícita la configuración completa y registrar después los param_groups reales. No estimar que el efecto fue pequeño y declarar por eso que la receta permaneció intacta.

**Se entrenó sobre un texto repetido ocho veces, no sobre los ocho documentos fijados**

_preflight_source() selecciona una fila del dataset y hace:

```python
encoded = tokenizer([text] * 8, ...)
```

Eso construye ocho secuencias físicamente presentes, pero todas contienen el mismo texto. Tampoco utiliza el manifest previo de los ocho artículos reconstruidos. El filtro de 400 tokens sólo permite cubrir parcialmente la segunda ventana; no garantiza los 513 tokens reales fijados para la prueba nominal.

Puede ser una prueba exploratoria de ejecución GPU, pero no es la carga de entrada que habíamos predeclarado.

Hay, además, una discrepancia concreta en el resumen de tokens: no todos los updates registran 1.352. En el ledger de shared_K1, el update 0 tiene 2.048 tokens válidos y el update 1 tiene 1.352. El primer update de shared_K4 también registra 2.048.

Por tanto, el reporte debe reconstruir los tokens por actualización desde los eventos, no generalizar el valor del último update.
