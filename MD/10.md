# 2. El siguiente gate cambia de pregunta: de coexistencia a composición

C1 respondió:

> ¿Puede un checkpoint mantener y entrenar todas estas capacidades simultáneamente?

El siguiente debe responder:

> **¿Puede el resultado producido por una primitiva convertirse en la entrada efectiva de otra, dentro de una misma trayectoria, sin que el oráculo reponga la información correcta?**

No basta con ejecutar:

```text
una tarea de retrieval
→ una tarea aritmética independiente
→ una acumulación independiente
```

Eso seguiría siendo coexistencia, aunque se empaquetara en un solo ejemplo.

Necesitamos:

```text
resultado recuperado por el modelo
→ determina la siguiente lectura
→ evidencia realmente recuperada
→ transformación aprendida
→ acumulación persistente
→ salida final
```

Propongo identificar esta fase como **`T1-MIX-O`**, donde `O` indica que el control sigue siendo oráculo.

## 3. El primer programa mixto no necesita nuevas primitivas

Empezaría por una composición **P → lectura de evidencia → W**, porque utiliza interfaces que ya existen y evita añadir al mismo tiempo transporte entre registros, nuevos opcodes y otra campaña de entrenamiento.

### Ejemplo mínimo

La memoria contiene relaciones:

```text
REL(a, b)
REL(b, c)
```

y evidencias vectoriales direccionables:

```text
VEC(b, e_b)
VEC(c, e_c)
```

junto con distractores.

Inicialización única:

$$
P_0=E(a),\qquad W_0=0.
$$

Programa:

| Paso | Instrucción oráculo                               | Dato que debe usar el modelo    |
| ---: | ------------------------------------------------- | ------------------------------- |
|    1 | `READ_P`, BLEND, P→P                              | El puntero actual \(P_0\)       |
|    2 | `ACCUM_W`, SELECT, P→W, transformación \(\tau_1\) | El **P producido en el paso 1** |
|    3 | `READ_P`, BLEND, P→P                              | El puntero que permaneció en P  |
|    4 | `ACCUM_W`, SELECT, P→W, transformación \(\tau_2\) | El **P producido en el paso 3** |
|    5 | `EMIT W`                                          | El workspace acumulado          |

El target externo es:

$$
W^*=A_{\tau_1}e_b+A_{\tau_2}e_c.
$$

La memoria relacional se busca con la ruta `READ_P` ya validada. La lectura de un vector concreto utiliza SELECT. **No hay que cambiar retrospectivamente el workspace histórico BLEND ni sus baselines.**

Este ejemplo prueba una transición que C1 todavía no exigía: que una dirección **producida por el modelo**, posiblemente con pequeñas diferencias respecto al embedding ideal, sirva correctamente como consulta para la siguiente primitiva.

### Diferencia concreta respecto al runner actual

En C1, `run_transform_batch()` asigna en cada ronda:

```python
state[:, SLOT_P, :] = memory_keys_logical[
    ..., batch["query_logical"][:, round_index]
]
```

Eso era válido allí: la instrucción proporcionaba una dirección explícita para aislar lectura y transformación. **En el programa mixto no se puede reutilizar esa asignación para sustituir un puntero que debía haber calculado la ronda anterior.**

Para MIX:

```text
Inicialización de P:
una vez, desde el input del programa.

Actualizaciones posteriores de P:
solo mediante las transiciones del modelo.
```

Esta es la restricción más importante del siguiente gate.

## 4. Qué puede indicar el oráculo y qué no

El oráculo puede proporcionar el programa: opcode, modo de lectura, slots fuente y destino, argumentos literales, transformación y longitud.

**No puede proporcionar los resultados de ejecutarlo.**

| Permitido                                | No permitido                                         |
| ---------------------------------------- | ---------------------------------------------------- |
| “Sigue una relación desde P”             | “El siguiente puntero correcto es b”                 |
| “Lee el vector cuya dirección está en P” | Índice físico de la fila que debería recuperar       |
| “Aplica la transformación \(\tau_2\)”    | Vector transformado correcto                         |
| Máscaras por tipo de fila y padding      | Máscara que deja legal solamente la respuesta        |
| Target y traza simbólica para evaluar    | Reinyectar esa traza en el estado durante el forward |

El generador debe tener un intérprete simbólico independiente para calcular targets y estados esperados. Su función es evaluar, **no asistir al modelo durante la ejecución**.

Tampoco debe existir un acceso del core a toda la memoria para compensar una lectura equivocada.

# 5. Primera ejecución: congelada, sin entrenamiento adicional

Autorizo implementar el ejecutor de programas y evaluar primero el **checkpoint final annealed de seed101**, elegido por convención y no porque tenga el mejor número.

Mantener:

```text
D=64
un checkpoint
un reader
un core
un commit
los mismos codebooks
los mismos modos SELECT/BLEND
```

La primera campaña debe variar relaciones, claves, orden de memoria, valores e instrucciones de transformación, pero mantener un tamaño pequeño y comparable con las pruebas existentes.

Empezaría con programas cortos de **4 y 6 actualizaciones útiles**, sin contar el padding `EMIT`, y varias secuencias de transformaciones. No aumentaría simultáneamente la memoria a cientos de filas ni la profundidad a decenas de rondas.

### Un estado persistente, no estados separados por subtarea

La máscara de presencia debe fijarse para todo el programa. Para el primer ejemplo basta P y W presentes desde el inicio.

No alternar:

```text
máscara de pointer task
→ máscara de workspace task
→ máscara de pointer task
```

porque la implementación reaplica la máscara después de cada ronda y pondría a cero los slots declarados ausentes. Eso podría borrar el workspace o el puntero entre operaciones.

Los slots que no son destino deben conservarse. `EMIT` no escribe ni reinicializa nada.

### Corrección por instrucción, no por batch

La corrección transformada debe ejecutarse únicamente para el `ACCUM_W` que la solicita. Un `READ_P`, un `EMIT` o una instrucción RAW del mismo batch no deben activar esa rama por el hecho de que otra muestra la utilice.

Esto debe mantenerse explícito en el ejecutor mixto, especialmente porque la API actual recibe `transform_id` y `correction_module` como argumentos de la llamada.

No hace falta otra red: hace falta un dispatch por instrucción correctamente definido.

## 6. Métricas y controles que distinguen composición real

Conservaría como criterio continuo inicial:

$$
\cos(W_{\mathrm{pred}},W^*)>0.999,
\qquad
\frac{\|W_{\mathrm{pred}}-W^*\|}{\|W^*\|}\le0.01.
$$

Es el gate funcional de la nueva composición, **no la obligación de reproducir el récord de \(10^{-5}\) de C1**. Para los estados y decisiones discretas, fijaría `≥99.9%` por familia de programas, además de registrar los errores exactos.

La evaluación debe guardar la traza:

```text
P después de cada READ_P
fila elegida en cada SELECT
payload recuperado
delta aplicado a W
W acumulado
slots que debían permanecer intactos
```

Los controles principales serían tres.

**Intervención sobre el puntero intermedio.** Sustituir el P producido por otra identidad válida que tenga evidencia distinta. La siguiente lectura debe seguir ese puntero intervenido. Comparar contra la ejecución simbólica alternativa, no limitarse a observar que “baja la accuracy”.

**Intervención sobre la memoria.** Mantener el mismo programa y punto inicial, pero cambiar una relación relevante. La respuesta debe seguir la nueva cadena. Así se descarta que el programa codifique implícitamente las direcciones o que se memorice una respuesta por plantilla.

**Conservación del estado.** Congelar P debe romper las cadenas que necesitan avanzar; reemplazar W debe perder las contribuciones anteriores; añadir `EMIT` no debe cambiar el resultado.

### No repetir una frontera demasiado simplificada

No exigiría automáticamente:

$$
R<L\Rightarrow\text{azar}
$$

para todos los programas. Algunas operaciones pueden cancelarse o producir accidentalmente el mismo resultado.

Para probar necesidad de profundidad, generar **ejemplos testigo** donde el dato que falta procesar cambia necesariamente el target y comparar las trazas. La longitud se mide en actualizaciones declaradas; no puede haber dos lecturas o varias primitivas ocultas dentro de una sola ronda para aparentar una frontera más favorable.

## 7. Después: incorporar ALU con un transporte explícito

Una vez que P→W funcione, añadiría la familia:

```text
seguir referencia
→ recuperar un valor numérico
→ utilizar ese valor en R
→ ejecutar ALU
→ emitir resultado
```

Aquí hay una interfaz que debe declararse antes de implementarla: **cómo pasa el valor recuperado desde E al registro R**.

El core actual utiliza R para la ALU; cambiar solamente `source_slot` no convierte automáticamente E en su registro de entrada. El commit aritmético devuelve además el resultado al codebook de 32 valores.

No se debe resolver mediante una asignación del target desde el harness.

Para esa ampliación aceptaría una **copia tipada explícita, sin parámetros**, desde E hacia R, siempre que ambos representen el mismo dominio numérico. Debe contar como una operación visible del programa y transportar el valor **predicho**, no el verdadero.

Esa extensión corresponde a la segunda familia de MIX, no hace falta introducirla para empezar el primer programa.

# 8. Qué pasa si la composición congelada falla

**No reabre C1.** C1 demostró coexistencia y estabilidad; no había demostrado aún que las distribuciones de estados producidas por una primitiva sean inmediatamente utilizables por todas las demás.

Una falla congelada debe localizarse en la primera transición incorrecta:

```text
¿P ya era incorrecto?
¿P era correcto al decodificar, pero SELECT no acepta su representación?
¿La lectura fue correcta y falló la transformación?
¿Se borró un slot que debía conservarse?
```

Primero se descartan problemas del ejecutor y de transporte. Si el camino es correcto pero necesita adaptación, se diseña el fine-tuning sobre programas mixtos conservando replay y la receta estabilizada. **No autorizaría ahora una campaña grande antes de medir esa línea base congelada.**

Los programas de prueba deben ser nuevos. Si posteriormente se entrena MIX, separar tanto los datos como determinadas secuencias de operadores entre entrenamiento y test; no basta con cambiar vectores dentro de las mismas plantillas para afirmar generalización composicional.
