Qué implica para Prioridad 2

No elegiría entre “runtime recurrente” o “runtime vocab” basándonos exclusivamente en K1 vs K4.

Diseñaría el runtime desde el principio con dos fronteras nativas independientes, pero no intentaría implementar ambas a la vez:

Native Runtime
├── RecurrentEngine
│   ├── forward
│   └── backward full-BPTT256
│
├── VocabLossEngine
│   ├── student vocab projection
│   ├── CE + KL
│   └── backward hasta projected/readout
│
└── TeacherHiddenView
    └── hidden-cache + exact lm_head

La arquitectura debe permitir que ambos frentes terminen nativos sin rehacer interfaces.

Pero implementaría primero el recurrente

No porque siempre sea el porcentaje mayor, sino porque tiene más headroom plausible:

es el loop propio de OMEGA;

contiene muchos small-GEMM/operaciones por token y por ronda;

escala directamente con K;

ya tenemos evidencia T0 de beneficios importantes por matrixización/cache residence;

PyTorch probablemente está relativamente mejor optimizado en la gran proyección vocabularia que en vuestro loop recurrente pequeño y secuencial.

Para K4 además representa casi la mitad del update.

Así que el orden que recomiendo es:

P2-R — native recurrent forward+backward
      K1 + K4
      bit-exact/equivalent oracle
      benchmark end-to-end

↓ reprofile canonical runtime

P2-V — native/fused vocab+CE+KL
      sólo si el residual sigue justificándolo

No construiría P2-R de una manera que obligue a dejar PyTorch permanentemente para vocab/loss. Sólo lo usaría como primera pieza.

Por qué no atacar ambos simultáneamente

Porque perderíamos causalidad.

Si reemplazamos recurrente + vocab/loss a la vez y obtenemos 1.7×:

no sabremos cuál pagó el trabajo;

un bug numérico tendrá una superficie enorme;

será difícil aislar gradientes;

y no sabremos si valía la pena construir una de las dos partes.

El patrón de esta campaña ha funcionado precisamente porque hemos ido cerrando una variable cada vez.

No hace falta decidir ahora “K de producción”

El kernel recurrente debe recibir K como parámetro y soportar al menos:

K=1
K=4

No lo hardcodearía a K4.

Así el benchmark nos dará dos datos distintos:

cuánto acelera el caso barato K1;

cuánto acelera el caso que más explota la recurrencia K4.

Después podremos decidir si el costo adicional de K4 sigue siendo aceptable.
