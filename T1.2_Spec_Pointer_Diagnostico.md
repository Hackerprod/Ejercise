# Spec T1.2 — Diagnóstico del pointer-chasing (Respuesta_3.md)

Fuente única: `MD/Respuesta_3.md`. Misma regla: nada se implementa sin cita textual. Contexto previo: `T1.1_Spec_Diagnostico_Correctivo.md` (Fase A/B/C), resultado seed101: matriz train 256-ejemplos llega a 100% en R≥H (H4/R4=100%, H4/R2=96.9%), held-out colapsa a 0-1.64%, dataset de 10k muestra señal monótona real pero techo bajo (H4: R1=7.57%/R2=12.55%/R4=15.74%) que no sube con 10x más steps.

**Veredicto de Sol**: la causa más probable es (c) arquitectura/parametrización del pointer slot, NO (a) escala de datos ni (b) grokking — al menos no todavía. **No escalar datos, steps ni semillas hasta pasar por esta secuencia.**

## Por qué la matriz memorizada no prueba nada todavía

`H4/R2=96.9%` en train es la prueba clave: si de verdad hace falta una lectura por ronda y R=2 no alcanza para 4 hops, un modelo con R=2 NO debería resolver H4 en absoluto. Que lo resuelva casi perfecto en train significa que memorizó una función directa `ejemplo completo→respuesta final`, no que ejecutó el algoritmo `x1=f(x0), x2=f(x1), x3=f(x2), x4=f(x3)`. Interpretación correcta: 100% train = capacidad paramétrica confirmada; ~0% held-out = algoritmo general no aprendido; H4/R2=96.9% train = shortcut de memorización confirmado.

## Hipótesis principal — el pointer slot se residualiza cuando debería reemplazarse

Implementación actual (Fase B de T1.1): `h_{r+1} = h_r + α·F(h_r)`. Para un puntero discreto esto está mal — la operación correcta es:

```text
p_{r+1} = Read(M, p_r)          (reemplazo completo)
```

no:

```text
p_{r+1} = p_r + α·Read(M, p_r)  (residual — lo que tenemos ahora)
```

Con residual, tras varias rondas el estado se convierte en una superposición: `p_r ≈ c_0·e_{x0} + c_1·e_{x1} + ... + c_r·e_{xr}`. El reader de la ronda siguiente recibe una mezcla de varios keys y recupera una mezcla de valores. **Esto explica simultáneamente**: progreso monotónico, techo bajo, error creciente con hops, memorización perfecta de ejemplos fijos, mala generalización — todos los síntomas observados a la vez.

Transición correcta propuesta:

```text
p̃_{r+1} = Reader(p_r, M)
p_{r+1} = Canonicalize(p̃_{r+1})       ← pointer slot: reemplazo, no residual
w_{r+1} = w_r + F_w(w_r, p_r, p̃_{r+1}) ← otros slots (workspace): sí pueden ser residuales
```

Separación de funciones: pointer slot = estado discreto actual (reemplazo); workspace slots = evidencia/cómputo continuo (residual).

## Segundo problema — α=1/√R rompe la homogeneidad del operador

`R=1→α=1.0, R=2→α≈0.707, R=4→α=0.5` — una "ronda" no representa la misma operación entre modelos con distinto R total. Pointer chasing necesita un operador homogéneo `p_{r+1}=f(p_r)` con la misma semántica sin importar cuántas rondas se van a ejecutar en total. Para el pointer slot: reemplazo completo, o gate fijo z=1, o z constante independiente de R — nunca dependiente de R.

## Tercer problema — posible memorización de identidad de keys

Si `key_17` usa siempre el mismo embedding entrenable, el modelo puede aprender regularidades específicas de esa key en vez de la regla abstracta "buscar valor asociado a la key actual". Un algoritmo genuino debe ser equivariante: `f(π(G),π(x)) = π(f(G,x))` para cualquier permutación π de labels. Fix: permutar labels aleatoriamente en cada ejemplo, o generar nuevos vectores de key por ejemplo, para que el modelo nunca pueda memorizar que una dirección concreta = una entidad concreta.

## Cuarto — error multiplicativo por ronda (hipótesis a verificar, no asumir)

`p^4 = 0.1574 → p ≈ 0.63` — un operador que acierta ~63% por paso da ~15.7% después de 4 pasos. No asumir que los errores son independientes, pero la coincidencia indica dónde mirar: medir el puntero interno después de cada ronda, no solo la respuesta final.

## No aceptar sin medir: "un Transformer también fallaría"

Plausible pero no demostrado. Requiere baseline real bajo las MISMAS restricciones (mismo reader, misma máscara, mismos parámetros, mismo dataset, mismo presupuesto) — el baseline importante es uno con la misma barrera informativa de una lectura por paso, no un Transformer con atención global libre.

## No apostar todavía por grokking

Necesita condiciones específicas no establecidas: ¿los 10k ejemplos son fijos o se regeneran online? ¿cuántas épocas representan 50k steps? ¿batch size? ¿qué parámetros reciben weight decay (¿los embeddings de key también?)? Sin esas respuestas, invocar grokking es prematuro — sobre todo habiendo indicios más concretos de un operador de un paso imperfecto y una representación no equivariante.

## Secuencia de diagnóstico — UNA SOLA SEMILLA, en este orden

### P0 — Oráculo del benchmark (sin entrenar nada)
```text
N = 16 o 32
grafo acíclico, sin self-loops, sin ciclos ≤ Hmax
keys one-hot
reader EXACTO (hand-coded, no aprendido): p_{r+1} = p_r @ A
```
Debe dar, sin ningún entrenamiento: `R<H → azar`, `R≥H → 100%`. **Si falla, el bug está en el generador/máscara/evaluador, no en el modelo — no seguir a P1 hasta que P0 pase perfecto.**

### P1 — Exactitud por ronda (con el modelo actual, Fase B/C tal como está)
Medir por ronda r: `pointer_acc_r`, `reader_entropy_r`, `reader_margin_r` (margen entre key correcto y segundo candidato), `old_pointer_mass_r` (masa retenida sobre el puntero anterior), `cosine(query_r, embedding_key_correcto)`. Decide si 15.74% es error multiplicativo (caso: accuracy cae ~fijo por ronda) vs error de readout (caso: accuracy por ronda alta pero resultado final bajo) vs problema anterior a la recurrencia (caso: r1 ya está bajo, 60-70%).

### P2 — Reemplazo del pointer slot
Cambiar SOLO esto: `pointer_next = reader_output` (sin residual, sin α=1/√R, sin gate aprendido). Otros slots (si los hay) conservan el residual pre-norm de Fase B.

### P3 — Codebook permutado
Reetiquetar aleatoriamente las keys en cada muestra (o generar vectores nuevos por ejemplo). Mismo problema abstracto. Si la accuracy se destruye al permutar, confirma que el modelo memorizaba identidades, no la regla.

### P4 — Un hop primero
Entrenar EXCLUSIVAMENTE H1. Criterio: held-out H1 ≥ 98-99%. **Si ni H1 generaliza, no tiene sentido probar H4 — el problema está en el reader/representación, no en la composición.** Solo si H1 generaliza: congelar el operador, evaluar H2/H3/H4. Si H1=99% pero H4 cae mucho → problema de estabilidad composicional/canonicalización.

### P5 — Supervisión intermedia (diagnóstico, no prueba final)
```text
L = L_final + λ·Σ_r CE(p̂_r, p_r*)
```
Si con targets intermedios generaliza → problema de asignación de crédito. Si tampoco generaliza → problema de representación/reader. Si generaliza con teacher-forcing pero falla en free-running → exposición/acumulación de error. **No usar esto como prueba final de generalización** (puede inducir shortcuts propios) — solo para localizar la causa.

## Árbol de decisión

| Resultado | Diagnóstico |
|---|---|
| Oráculo (P0) no consigue 100% | Bug restante en benchmark |
| Oráculo pasa, H1 aprendido falla | Reader/codebook |
| H1≥99%, H4≈p⁴ | Error acumulativo |
| Teacher forcing pasa, free-running falla | Estado fuera del manifold |
| Auxiliar por ronda pasa, final-only falla | Asignación de crédito |
| Permutación de keys destruye accuracy | Memorización de identidades |
| Baseline restringido también falla | Régimen de datos/benchmark |
| Todo lo anterior pasa, 10k sigue limitado | Recién ahí escalar datos/capacidad |

## Decisión / orden de ejecución

```text
NO escalar datos, steps ni semillas todavía.
Orden obligatorio: oráculo exacto → accuracy por ronda → pointer replacement → keys permutadas → un hop primero.
```

El objetivo inmediato NO es subir H4 de 15% a 20% — es producir la firma algorítmica correcta (`R<H→azar`, `R≥H→salto abrupto y generalización`). Hasta no observar esa frontera, más datos solo permitirían memorización más extensa, no aprendizaje real.
