**Sí: autorizo C1 con seed101, entrenamiento conjunto y STE únicamente para las instrucciones SELECT. No hace falta otra campaña de inferencia antes.**

Revisé `9ceaaf4`, el reader y los JSON publicados. La compatibilidad conserva las métricas históricas; el aislamiento mixto registra diferencias máximas de payload de `0` y `1.788×10⁻⁷`, por debajo de `atol=10⁻⁶`. El C0-reader integrado conserva el peor error final por celda de evaluación de `0.0087313`. Esta es una revisión de código y resultados publicados, no una nueva ejecución de los checkpoints.

Las diferencias entre batch mixto y ejecuciones separadas son compatibles con la aritmética de punto flotante: PyTorch no garantiza identidad bit a bit entre una operación por lotes y sus ejecuciones por separado. No constituyen motivo para reabrir esta validación. ([PyTorch Documentation][1])

**Lo nuevo que debe validarse ahora es el backward de SELECT y la conservación de las siete tareas mientras los parámetros compartidos se actualizan.**

## 1. El forward está listo; STE todavía debe incorporarse

En el código actual, SELECT obtiene el payload con `gather` sobre el índice elegido mediante `argmax`. Eso implementa correctamente la selección dura, pero no proporciona a los scores el gradiente sustituto que queremos probar en C1. BLEND sigue utilizando su suma ponderada.

Mantener:

```text
read_mode = BLEND  → mezcla en forward y backward
read_mode = SELECT → selección dura en forward
```

Para SELECT durante entrenamiento, añadir:

$$
p=\operatorname{softmax}(s),
\qquad
h=\operatorname{onehot}(\arg\max s),
$$

$$
a_{\mathrm{ST}}
=
h+\bigl(p-\operatorname{stopgrad}(p)\bigr),
$$

$$
Y=a_{\mathrm{ST}}V.
$$

Así, el forward utiliza la fila seleccionada y el backward hacia los scores utiliza la relajación soft. **Es un gradiente sustituto, no el gradiente exacto de argmax.** La documentación de PyTorch describe este mecanismo de salida one-hot con gradiente de la distribución suave. ([PyTorch Documentation][2])

No añadiría un tercer valor al vocabulario de `read_mode`. STE es una política de entrenamiento de SELECT, no otra instrucción semántica.

Durante evaluación:

```text
SELECT → argmax + gather
```

Sin muestreo, sin Gumbel y sin cambiar la temperatura. No queremos introducir a la vez selección estocástica y entrenamiento conjunto.

### Una precaución de implementación

Aplicar STE a **los pesos de selección**, antes de combinarlos con los values. No utilizar sin comprobar algo como:

```python
payload_hard + payload_soft - payload_soft.detach()
```

porque esa expresión también añade un camino de gradiente soft hacia los values. No es necesariamente el backward que hemos especificado.

Con \(a_{\mathrm{ST}}V\), el gradiente directo hacia los values corresponde a la selección dura, mientras que el gradiente hacia los scores utiliza \(p\). Si keys y values comparten parámetros, sus contribuciones posteriores se sumarán normalmente; no confundir ese parámetro compartido con el gradiente local de cada entrada.

## 2. Solo falta un preflight unitario del backward, no otro gate experimental

Incluiría estos tests como parte de la implementación de C1:

| Comprobación                                          | Criterio                                                                       |
| ----------------------------------------------------- | ------------------------------------------------------------------------------ |
| Forward SELECT con STE frente a SELECT con `gather`   | Mismo índice y mismo payload, dentro de la tolerancia numérica declarada       |
| Gradiente hacia scores                                | Coincide con el sustituto soft especificado en un fixture no degenerado        |
| Gradiente directo hacia values                        | Corresponde a la fila seleccionada                                             |
| Batch mixto SELECT/BLEND                              | Gradiente conjunto coincide con la suma ponderada de las ejecuciones separadas |
| Filas ilegales, ejemplos sin lectura y padding `EMIT` | Sin payload espurio, sin NaN y sin contribuciones indebidas                    |

**No se debe exigir que una diferencia finita del forward argmax coincida con STE.** Eso probaría un contrato distinto. Se comprueba el backward sustituto que hemos decidido implementar.

Para comparar gradientes de batch mixto y muestras separadas, igualar exactamente la reducción de la pérdida: una media sobre dos ejemplos se compara con la media de sus dos pérdidas, no con su suma.

Si estos tests pasan, comienza la corrida. No hace falta volver a pedirme autorización.

## 3. C1 debe partir de los modelos aprobados, no reconstruirlos desde cero

La inicialización queda fijada:

| Componente                               | Procedencia y tratamiento                        |
| ---------------------------------------- | ------------------------------------------------ |
| Reader, core, codecs, ALU y decoders     | Checkpoint U0-A validado                         |
| Corrector y embeddings de transformación | C0-oracle oficial `network_trainable`            |
| Workspace histórico                      | BLEND, ruta RAW, sin corrector nuevo             |
| Acumulación transformada                 | SELECT, dirección explícita, corrector aprendido |
| `read_mode`                              | Campo de instrucción, sin embedding nuevo        |
| Routing                                  | Sigue siendo oráculo                             |

El corrector debe registrarse dentro del **único modelo conjunto**. Importar sus pesos, no arrastrar una segunda `frozen_base`, otro reader o una copia del núcleo.

La corrección tampoco debe activarse simplemente porque `read_mode=SELECT`. Son decisiones distintas:

```text
read_mode:
cómo obtener el payload

transformación/RAW:
qué hacer con él

ACCUM_W:
cómo escribir el resultado en W
```

Eso permite conservar `SELECT + RAW` como lectura y acumulación exactas, y evita asociar ocultamente una implementación a una tarea.

Para el experimento principal de C1, el reader y el core deben poder actualizarse junto con el corrector, manteniendo las congelaciones estructurales ya declaradas —por ejemplo, la corrección antigua de U0-A que debía permanecer en cero—. **Una corrida con toda la base congelada sería un control útil, pero no demostraría estabilidad bajo entrenamiento conjunto.**

## 4. Protocolo de entrenamiento: conservar la receta y corregir la contabilidad

La configuración aprobada de U0-A utiliza batches de 128, `D=64`, AdamW con `lr=3e-4`, un step por superstep y replay secuencial de cinco batches de tabla elemental por uno de composición. Esa es la receta que debe conservarse, no el currículo uniforme que ya falló.

Para C1:

$$
\mathcal L_{\text{joint}}
=
\frac{
\sum_{t=1}^{6}\mathcal L_t
+
\mathcal L_{\text{transformada}}
}{7}.
$$

Un superstep contiene un batch de cada tarea, incluida la nueva. La tarea secuencial conserva su calendario 5:1; la tabla de replay no se convierte accidentalmente en una octava tarea.

La secuencia del optimizador debe ser:

```text
zero_grad(set_to_none=True), una vez
→ acumular las siete pérdidas/gradientes
→ clipping global, si está configurado
→ optimizer.step(), una vez
```

**No ejecutar `zero_grad()` entre tareas.**

### Precisión importante sobre `grad=None`

El aislamiento no significa que un módulo deba permanecer inmóvil después de cualquier superstep donde apareció una tarea que no lo utiliza.

Por ejemplo, el corrector está inactivo en los seis batches históricos, pero activo en el séptimo. Es correcto que cambie después del step conjunto.

La inmovilidad post-step se exige cuando el módulo:

> **No intervino en ninguno de los microbatches de ese superstep.**

No deben limpiar el gradiente de un módulo al llegar a una tarea que no lo usa: podrían borrar una contribución válida acumulada anteriormente.

### Learning rate y presupuesto

Para esta primera corrida conservaría `3e-4` en los componentes entrenables, incluido el corrector precargado. Es una decisión de fine-tuning para C1: **no trasladaría automáticamente el `0.01` de su entrenamiento aislado**.

Mantener `weight_decay=0` en corrector y componentes tipados pequeños, y la configuración ya validada para el resto. No añadiría simultáneamente PCGrad, nuevos adapters, schedules de temperatura o más anchura.

Autorizo **hasta 12,000 supersteps, seed101**, con evaluaciones de validación en step 0, 100, 500, 1000 y después periódicamente. El objetivo de los puntos tempranos es localizar una regresión antes de gastar todo el presupuesto, no seleccionar modelos usando el test.

## 5. El riesgo nuevo es que el entrenamiento deteriore un selector que ya funciona

SELECT ya pasa en inferencia congelada. Ahora sus scores recibirán gradientes de la tarea transformada, además de los que llegan desde las tareas históricas.

No debemos asumir que eso lo mejorará automáticamente. **El propósito de C1 es comprobar que esas actualizaciones son compatibles.**

Por eso separaría siempre estas métricas:

```text
selección top-1 por ronda
error del payload respecto a la fila solicitada
error de transformación con lectura oráculo
error completo con lectura real
```

La lectura de un fallo queda entonces definida:

| Resultado durante C1                                       | Interpretación inmediata                                                                 |
| ---------------------------------------------------------- | ---------------------------------------------------------------------------------------- |
| Baja top-1; corrector con oráculo sigue bien               | Se deterioró el direccionamiento                                                         |
| Top-1 permanece perfecto; empeora el corrector con oráculo | Se deterioró la transformación                                                           |
| Ambos aisladamente bien; composición falla                 | Revisar trayectoria, commit y enmascarado                                                |
| Solo empeora workspace histórico                           | Revisar la ruta BLEND compartida y la exclusión del corrector                            |
| Baja ALU H1                                                | Revisar replay, cobertura y actualización de parámetros antes de culpar a la recurrencia |

No respondería a cualquiera de esos casos aumentando indiscriminadamente los steps.

## 6. Criterios de cierre: conservar los ya aprobados

**No añadiría ahora tareas más largas, memorias más grandes ni otro requisito científico.** Primero cerrar coexistencia bajo actualización conjunta.

### Seis tareas históricas

Conservar sus criterios de U0-A, sus curvas por profundidad y su baseline correspondiente. Para workspace histórico, comparar contra el baseline BLEND post-refactor, no contra el cero ideal de otro experimento.

Sus valores actuales en seed101 son aproximadamente `0.000253`, `0.000425` y `0.001438` para H2/H4/H6. No utilizar el umbral más permisivo de la tarea transformada para ocultar una regresión de RAW.

### Tarea transformada

Mantener, por profundidad y transformación:

$$
\text{coseno}>0.999,
\qquad
\text{error relativo final}\leq0.01,
$$

y el criterio ya establecido para el error del delta por ronda. Conservar top-1 y error de payload como métricas separadas, además de las ablaciones de corrección e instrucción.

### Un detalle decisivo: step 0 no puede ser el único “ganador”

Los componentes ya pasan antes de entrenar. Por tanto:

> Elegir el checkpoint de step 0 porque es el mejor no demuestra que C1 haya funcionado.

Guardar el mejor checkpoint de validación, pero reportar también el **checkpoint final entrenado** y la trayectoria de métricas. Para cerrar C1 debe existir evidencia de que el modelo conserva las tareas después de actualizaciones conjuntas reales, no solamente antes de ellas.

Del mismo modo, registrar los parámetros entrenables y sus actualizaciones efectivas. No exigir que todos cambien en cada step, pero sí descartar que el supuesto joint haya dejado congelados por accidente los componentes cuya estabilidad se pretende probar.
