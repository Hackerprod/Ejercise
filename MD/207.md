Prefiero una tercera opción: no cambiar el modelo y no copiar el peso. Hay que hacer que la C-ABI del kernel soporte esa vista strided directamente.

El slice:

prelude.weight[:, D:]

no es contiguo, pero su layout es perfectamente regular:

shape      = [state_count, D]
stride_col = 1
stride_row = 2*D

Así que el kernel no debería asumir:

C++
w[row * D + col]

sino:

C++
w[row * row_stride + col]

Para PyTorch:

row_stride = 2*D

Para el runtime nativo final, si guardamos esa matriz empaquetada:

row_stride = D

Mismo kernel. Cero copia.

Por qué esta opción es mejor

No elegiría (a) porque rompe innecesariamente la representación congelada de prelude.weight, nombres de parámetros y compatibilidad de checkpoints históricos.

No elegiría (b) porque introduce un costo artificial que existe sólo por el bridge temporal. Y sí: si usáramos esa solución, la copia tendría que contarse dentro de T_update, porque la ruta candidata la necesita para funcionar. Sacarla del reloj falsearía R2.

Pero no hace falta pagar ese costo.

Cambio de ABI

Haría algo conceptual como:

C++
struct OmegaMatrixViewF32 {
    const float* data;
    size_t rows;
    size_t cols;
    ptrdiff_t row_stride;   // in float elements
};

o, si quieren mantener la API mínima:

C++
const float* state_part_weight;
size_t state_part_weight_row_stride;

Preferiría el descriptor genérico porque vamos hacia un runtime completo y probablemente reaparezcan vistas/leading dimensions.

No hace falta soportar cualquier tensor arbitrariamente strided. Para v1:

col_stride must be 1
row_stride >= cols

Fail-closed si no.

Cómo encaja con autograd

Muy importante: el bridge Python debe pasar el tensor-view real como argumento de autograd.Function, no sólo esconder su data_ptr().

Algo así conceptualmente:

Python
Run
state_weight = model.prelude.weight[:, D:]

OmegaRecurrentFunction.apply(
    token_part,
    previous_state,
    state_weight,
    ...
)

En forward:

state_weight.data_ptr()
state_weight.stride(0) == 2*D

se pasan a la DLL.

El C++ lee directamente del almacenamiento original.

En backward, el kernel puede producir:

d_state_part_weight
shape [state_count, D]
contiguous

y el autograd.Function.backward() devuelve ese gradiente para state_weight.

PyTorch se encarga de propagar el gradiente de la vista hacia:

prelude.weight[:, D:]

mientras la ruta normal de token_part aporta el gradiente de:

prelude.weight[:, :D]

Ambos terminan acumulándose correctamente en el mismo parámetro base prelude.weight.

Eso es exactamente lo que queremos validar en R2.

Gate previo obligatorio

Antes del benchmark real añadiría un test específico porque este cambio toca el acceso del kernel.

Dos fixtures:

PACKED
    shape [state_count,D]
    row_stride=D

STRIDED
    backing [state_count,2D]
    view begins at +D
    row_stride=2D

Mismos valores lógicos.

Exigir:

forward packed == strided
backward packed == strided

bajo la política numérica ya congelada.

Y un test negativo:

row_stride < D
→ reject

También verificar en el bridge real:

state_weight.stride() == (2D,1)

en vez de asumirlo silenciosamente.

Rendimiento

La indexación strided no debería añadir un costo importante.

En el inner loop C++:

C++
const float* row =
    state_part_weight.data + r * row_stride;

y después:

C++
row[c]

El stride sólo se aplica una vez por fila.

Y no cambia la cantidad real de datos usados: sigues leyendo únicamente la mitad state de cada fila, aunque entre filas haya la mitad token que no consumes.

En el runtime final puedes almacenar ambos pesos separados si quieres; sólo configuras:

row_stride=D

sin tocar el kernel.

Esto también preserva el principio de Addendum 235

El objetivo era:

la DLL que validamos ahora debe ser la misma pieza que sobreviva cuando PyTorch desaparezca.

Agregar soporte de leading dimension hace la biblioteca más independiente de PyTorch, no menos.

Permite recibir:

vistas PyTorch hoy;

buffers packed C++ mañana;

quizá otros layouts futuros,

sin que la matemática del kernel cambie.

Decisión formal
P2-R2 prelude state weight

DO NOT:
    split frozen model parameter
    copy/pack once per update

AUTHORIZED:
    strided matrix view in native C ABI

PyTorch bridge:
    passes real non-contiguous view
    data_ptr + row_stride
    view remains autograd input

Native backward:
    returns contiguous logical gradient
    PyTorch view backward scatters/accumulates
    into combined prelude.weight

Final runtime:
    may use packed row_stride=D
    same kernel unchanged

Y si por alguna razón técnica el bridge no puede devolver correctamente el gradiente a través de esa vista, entonces revisaría la alternativa de pasar el prelude.weight completo con offset/stride. No saltaría directamente a copiar cada update.

Así que no tocaría el modelo compartido ni contaminaría el benchmark con una materialización artificial. Añadiría soporte real de leading dimension al runtime.
