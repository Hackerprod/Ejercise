## Decisión

**Adoptaría top-1 para las lecturas cuya semántica es recuperar una fila concreta. No intentaría cerrar esta brecha aumentando la temperatura.**

Para C0, mantendría el reader congelado y usaría selección dura directamente. Para el entrenamiento conjunto posterior, conservaría ese mismo forward duro y probaría **straight-through como gradiente sustituto**, sin introducirlo todavía en la evaluación congelada.

La auditoría también registra top-1 correcto en todas las rondas activas y las 12 comparaciones de tensores con igualdad exacta. **La sospecha de que se estaba utilizando un reader sin entrenar queda descartada.**

La conclusión precisa es:

> **En las lecturas evaluadas, el reader ya selecciona correctamente la dirección. La mezcla soft introduce una distorsión que desaparece al transportar íntegramente la fila seleccionada.**

No es que todo el sistema pase a tener error cero: el corrector conserva su error propio, aproximadamente al nivel de C0-oracle. Lo que desaparece es la contribución adicional del reader.

También corrijo mi descripción del corrector: el evaluador carga explícitamente `u0c_c0_oracle_seed101_network_trainable`, construye el modelo con `train_residual_network=True` y su configuración declara la rama residual entrenable. **El análisis como transformación afín no describe esa campaña y no debe utilizarse para diagnosticarla.**

### No hace falta ejecutar C para tomar esta decisión

La descomposición \(u/v+\kappa\) sigue siendo útil para explicar cuantitativamente el error de la variante soft, pero **ya no debe bloquear el avance**.

La intervención top-1 respondió la pregunta de ingeniería: con los mismos pesos y el mismo target externo, eliminar la mezcla elimina el error de lectura. No necesitamos conocer todas las covarianzas del mecanismo que vamos a dejar de usar en esta operación.

## 2. La regla arquitectónica: seleccionar no es mezclar

Hasta ahora se había utilizado una misma fórmula para dos operaciones semánticamente diferentes:

$$
Y=\sum_j p_jV_j.
$$

Eso puede ser apropiado cuando se busca una combinación de evidencias. Pero aquí la instrucción significa:

```text
Lee el contenido de esta dirección.
```

No:

```text
Devuelve un promedio del contenido de esta dirección
y de varias direcciones parecidas.
```

Para una lectura direccionada, propondría:

$$
j^*=\arg\max_{j\in\mathcal L_r}s_j,
\qquad
Y_r=V_{j^*},
$$

donde \(\mathcal L_r\) es el conjunto de filas legales.

El modelo sigue decidiendo **qué fila leer**. La primitiva de lectura conserva exactamente **qué contiene esa fila**.

Esta decisión no añade la respuesta desde el generador ni sustituye la consulta aprendida por un índice oráculo. El evaluador actual obtiene `selected` de `result.attention.argmax`, y solo utiliza el índice esperado para calcular accuracy. Esa separación está bien implementada.

### Un reader compartido, dos políticas explícitas

Mantendría un solo scorer, los mismos codecs y las mismas máscaras, pero distinguiría:

| Política | Semántica                                  | Payload            |
| -------- | ------------------------------------------ | ------------------ |
| `SELECT` | Recuperar un registro individual           | Fila top-1 íntegra |
| `BLEND`  | Combinar deliberadamente varias evidencias | Suma ponderada     |

**La política pertenece a la instrucción o al contrato de lectura, no al `task_id`.** Dos tareas que solicitan una fila individual deben usar la misma política.

Para el cambio inmediato, aplicaría `SELECT` a la lectura de evidencia individual de `ACCUM_W`. No cambiaría simultáneamente todas las rutas de `READ_P` y `READ_E`: primero se incorpora esta modificación y se ejecutan las regresiones. Después se puede homogeneizar el resto de las operaciones cuya semántica también sea selección.

Esto no convierte el sistema en varios readers especializados. Cambia la forma de materializar el resultado de un único mecanismo de direccionamiento.

## 3. Por qué prefiero top-1 a afilar el softmax

Afilar la atención podría bajar el error por debajo de `0.01`, pero no resuelve tan directamente el contrato de lectura.

Si la fila correcta es \(k\), la contaminación del payload es:

$$
Y-V_k
=
\sum_{j\ne k}p_j(V_j-V_k).
$$

Por tanto:

$$
\|Y-V_k\|
\le
(1-p_k)\max_{j\ne k}\|V_j-V_k\|.
$$

Una misma fuga de probabilidad puede producir errores diferentes cuando cambian las normas de los valores o sus distancias. Aumentar el número de distractores también puede cambiar la masa total fuera de la fila seleccionada.

Con top-1, **condicionado a elegir bien la dirección**, el error de transporte es cero independientemente del contenido de las demás filas.

Además, multiplicar todos los logits por una constante positiva no cambia su argmax. Cuando el ranking ya es correcto, afilar sirve para aproximar mediante una mezcla lo que una selección directa ya realiza exactamente.

Conservaría la temperatura como parámetro de la relajación usada durante entrenamiento o como control experimental. **No la convertiría en el mecanismo principal de precisión de una lectura individual.**

En el source actual, `attention_temperature` multiplica los logits, tal como señalaste; cualquier calibración debe respetar esa convención.

## 4. Top-1 no impide entrenar el corrector; afecta al aprendizaje de la selección

Hay que separar tres situaciones.

### C0: reader y consultas congelados

Usar top-1 directamente. El corrector puede seguir recibiendo gradientes respecto a sus propios parámetros, aunque el payload proceda de una selección discreta.

**Aquí no hace falta straight-through.**

### Joint: queremos entrenar las direcciones desde la pérdida final

El argmax no proporciona el gradiente ordinario necesario para aprender cómo cambiar de fila. En ese caso, straight-through permite mantener un forward duro y utilizar una relajación suave para el backward. Es un estimador sustituto, no el gradiente exacto de la selección discreta. La literatura original lo presenta como una heurística de estimación de gradientes para decisiones no suaves. ([arXiv][1])

Mi candidato para C1 sería:

$$
p=\operatorname{softmax}(s),
\qquad
h=\operatorname{onehot}(\arg\max s),
$$

$$
a_{\mathrm{ST}}
=
h+\left(p-\operatorname{stopgrad}(p)\right),
$$

$$
Y=a_{\mathrm{ST}}V.
$$

En el forward:

$$
a_{\mathrm{ST}}=h.
$$

En el backward hacia los scores se utiliza la derivada de \(p\). Este patrón de salida discreta con gradiente de una relajación soft está documentado también en PyTorch. ([PyTorch Documentation][2])

El fragmento central, aplicado **solo a ejemplos con al menos una fila legal**, sería:

```python
# scores ya incluye la escala elegida; no volver a aplicarla aquí.
masked_scores = scores.masked_fill(~legal_rows, -torch.inf)

selected = masked_scores.argmax(dim=-1)
soft = masked_scores.softmax(dim=-1)

hard = torch.zeros_like(soft).scatter(
    dim=-1,
    index=selected.unsqueeze(-1),
    value=1.0,
)

weights = hard + (soft - soft.detach())
payload = torch.einsum("bm,bmd->bd", weights, memory_values)
```

Durante inferencia usaría directamente `gather` sobre la fila seleccionada, sin calcular una mezcla de valores.

**No usaría `gumbel_softmax` como sustitución automática:** esa función introduce muestreo Gumbel, mientras que lo validado aquí es un argmax determinista. La operación de muestreo y el truco straight-through no son lo mismo. ([PyTorch Documentation][2])

### Reader congelado, pero query producida por un módulo entrenable

Esta situación merece cuidado: congelar los parámetros del reader **no elimina la necesidad de transmitir gradiente a quien produce la consulta**. Si queremos que la pérdida final enseñe al núcleo cómo formar \(P_r\), un argmax puro corta esa vía.

Por eso la decisión sobre STE depende del **camino de aprendizaje**, no solamente de si `memory_reader.parameters()` está congelado.

### Qué debe comprobar el test de STE

No repetiría un `gradcheck` por diferencias finitas esperando que coincida con el forward argmax. Ese no es el contrato del estimador.

Los tests adecuados son:

* El forward de `SELECT_ST` coincide con la selección dura.
* El gradiente hacia los scores coincide con el sustituto soft declarado.
* Los gradientes hacia los values corresponden a la fila seleccionada.
* Filas enmascaradas no reciben contribución.
* Sin filas legales, se devuelve payload cero y `valid=False`, sin aceptar un argmax arbitrario.

Comprobé localmente el patrón anterior con tensores sintéticos: produjo igualdad exacta con la selección dura y los gradientes prescritos hacia scores y values. Eso valida el patrón básico, **no todavía la estabilidad de entrenamiento de C1**.

## 5. Hay un límite de cobertura importante en la prueba actual

El evaluador fija:

```python
MEMORY_ROW_IDS = tuple(range(10, 16))
```

y utiliza esas seis claves en todas las muestras. Las consultas recorren esas filas cíclicamente y cada ronda reconstruye \(P\) con el embedding de la dirección solicitada. Los valores gaussianos cambian entre ejemplos; las seis direcciones no.

Esto es válido para aislar el problema observado. Pero significa:

> **Tenemos muchas evidencias nuevas y programas de transformación, evaluados sobre seis patrones de direccionamiento fijos.**

No debemos describirlo todavía como una garantía de lectura perfecta sobre todo el codebook, memorias más grandes o consultas recurrentes predichas.

No exige otra campaña de entrenamiento. Antes de promover `SELECT` al reader integrado, haría una regresión de inferencia con claves válidas muestreadas del codebook, orden físico de filas permutado y valores nuevos. Mantendría primero seis filas para cambiar solo la identidad de las direcciones.

Si top-1 falla allí, el fallo será visible como **error de selección**, en lugar de quedar mezclado con un pequeño error continuo del payload. Eso es una ventaja diagnóstica.

Tampoco usaría una probabilidad soft alta como certificado universal de dirección correcta. Una lectura dura incorrecta sigue siendo incorrecta; la interfaz debe conservar el índice elegido, el margen y la validez para poder diagnosticarla.

## 6. El cambio todavía está en el evaluador, no en el reader integrado

Este es el paso de implementación pendiente.

En `evaluate_u0c_c0_reader.py` se calcula `hard_payload` a partir de la atención y los values. Pero el `SharedMemoryReader` publicado todavía devuelve el payload mediante:

```python
payload = torch.einsum("bm,bmd->bd", attention, values)
```

Es decir, **top-1 está validado como intervención externa, pero aún no es la política ejecutada por el módulo compartido**.

La implementación siguiente debe trasladar únicamente esa elección de payload al reader:

```text
Mismos parámetros.
Misma query.
Mismos scores.
Misma máscara.
Mismo conjunto de filas.
Nuevo read_mode explícito.
```

No cambiar temperatura, proyecciones, codebook y política de selección en el mismo commit.

`ReadResult` debería distinguir la distribución soft diagnóstica del resultado realmente utilizado:

```text
payload
selected_index
attention_soft
selection_margin
valid
read_mode
```

Así el evaluador no confundirá nuevamente “masa sobre el target” con “fila seleccionada correctamente”.

Una última precisión de hardware: seleccionar un único value puede evitar la mezcla de todos los values en inferencia, **pero el scorer actual sigue comparando la consulta con todas las keys**. Top-1 no convierte por sí solo el lookup en acceso de coste constante ni demuestra una aceleración CPU. Esa medición pertenece al runtime posterior.

**La decisión de fondo es esta: aprender dónde leer y copiar exactamente lo leído son responsabilidades distintas. Para una memoria direccionable, elegiría top-1 como semántica de lectura; reservaría la mezcla soft para operaciones que realmente pidan combinar evidencias, y usaría una relajación únicamente donde haga falta aprender la selección.**
