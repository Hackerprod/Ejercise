No hace falta ejecutar benchmark con ese build; /Qvec-report es diagnóstico de compilación. Después se recompila limpio sin ese flag para performance.

Quiero por loop:

source line / function
vectorized: yes/no
reason code

MSVC documenta, por ejemplo, 1200 para dependencia entre iteraciones, 1203 para accesos no contiguos y 1303 cuando considera que hay muy pocas iteraciones para que vectorizar valga la pena.

Árbol de decisión

Si los GEMM críticos aparecen como no vectorizados, especialmente por dependencia/reducción, aliasing o patrón de acceso, entonces:

OPT1B = GO
explicit AVX2 microkernels
FC1 → FC2 → QKV → OutProjection

Eso justificaría directamente escribir intrinsics manuales.

Si el reporte dice que ya están vectorizados, no escribiría inmediatamente los cinco microkernels. Primero inspeccionaría el assembly de esos loops para confirmar que realmente aparecen operaciones YMM útiles y cuánto código escalar queda. Si ya usa AVX2 correctamente y seguimos en 9.8×, entonces el gran problema probablemente sea otro: estructura de loops, ausencia de threading, reutilización/cache, overhead por reductions, o kernels demasiado pequeños/mal bloqueados.

Y Attention lo dejaría último incluso si no vectoriza. Con S=8, sus matrices son diminutas; FC1/FC2/QKV siguen siendo candidatos mucho más fuertes a explicar el grueso del 75%.
