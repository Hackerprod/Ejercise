Sí. Autorizo implementar OPT2 con ese diseño, con una sola modificación obligatoria: el caso profiling + T>1 no debe quedar simplemente documentado; debe quedar fail-closed mientras el profiler global no sea thread-safe.

El diseño principal está bien resuelto:

T=1:
    hard branch
    llama directamente al kernel serial ya certificado
    mismo workspace
    cero reducción
    cero threads
    debe permanecer idéntico al baseline actual

T=2 / T=4:
    sharding fijo por batch
    un dispatch + un join por forward/backward
    cero barreras internas
    pesos read-only compartidos

Backward:
    d_token_part / d_previous_state disjuntos
    13 parameter-grad buffers privados por worker
    cero atomics
    reducción final determinista worker 0→T-1

Eso es exactamente la estrategia que quería.

Cambio obligatorio: profiling

Si el profiler actual tiene estado global no seguro para concurrencia, congelaría:

OMEGA_PROFILE_INTERNAL + runtime_threads > 1
    => REJECT / explicit error

No quiero:

mutex por cada scope en el hot path;

atomics añadidos sólo para poder perfilar;

ni una carrera latente que alguien active meses después.

Para perfilar threading en el futuro, se diseña otro profiler con buffers per-worker y merge posterior. Pero no ahora.

La build Release normal sigue:

profiling compiled = false

por lo que no afecta OPT2.

Dos requisitos adicionales que fijaría ahora

1. Cero allocations dentro de forward()/backward().

El omega_runtime_create() debe reservar:

workers;

scratch por worker;

gradientes privados;

coordinación/sincronización.

Después de create, el hot path no debe hacer new, malloc, std::vector resizing ni crear threads. Si necesita más memoria, workspace_bytes() debe declararla antes.

2. Determinismo exacto para una misma T.

Como la partición de batches es fija y la reducción final también:

T=2 run A == T=2 run B
T=4 run A == T=4 run B

idealmente byte/hash exacto.

No espero T=4 == T=1 bit a bit; para eso aplican los gates numéricos ya congelados.

threading + affinity
